[(1) eval編](/2026/10/24/fluxpinel-1.html)と[(2) DSLプラグイン編](/2026/10/24/fluxpinel-2.html)のつづきです。今回は、動いているバイナリにソケットでつなぐコンソールを作ります。つなぐ先として、いちばん面白そうなのがRailsアプリです。この記事では、RoundhouseでSpinel向けに変換したRailsアプリにFluxpinelを組み込んで、動いているサーバの中をソケット越しにのぞいてみます。

いまのところ無改造というわけにはいきませんが、Roundhouseの出力を手で少し直せば動くところまで来ました。Fluxpinel側でどこまでできているか、手作業をなくすためにRoundhouseとSpinelに何を提案したいか、実現したらRailsアプリでどう使えるか、を書きます。

## Roundhouseがつくるバイナリ

Roundhouse[^rh]は、Railsアプリを別の言語のプロジェクトとして出力するツールです。ターゲットにはRust、Go、TypeScriptなどがあり、そのひとつがSpinelでコンパイルするRubyです。

[^rh]: [https://github.com/rubys/roundhouse](https://github.com/rubys/roundhouse)

Spinel向けの出力では、RoundhouseはRailsアプリを「メタプログラミングを使わないRuby」に書き替えます。Active RecordやAction Controllerにあたるフレームワークの部分も、Spinelでコンパイルできる形のRubyとして一緒に出力されます。それを`spin build`[^spin]でコンパイルすると、ひとつの実行ファイルになります。データはSQLiteのファイル（既定では`storage/development.sqlite3`）に置きます。

[^spin]: `spin`はSpinelのプロジェクトツールです。依存するパッケージを解決して、プロジェクト全体をひとつのCの翻訳単位にしてからコンパイルします。

Roundhouseのリポジトリには、変換を確かめるための小さなブログアプリを作るスクリプト（`scripts/create-blog`）が入っています。`rails new`とRails 8のscaffoldで、記事（Article）とコメント（Comment）のアプリを作るもので、Turbo StreamsとAction Cableも使っています。RoundhouseのCIは、このアプリを各言語に変換して動かし、同じURLに本物のRailsと同じHTMLを返すかを比べています。この記事でも、このブログアプリを題材にします。

できあがったバイナリはHTTPサーバです。接続ごとにSpinelのグリーンスレッドを1本立てて、CPUのコアごとにOSのスレッドを1本使います。リクエストの読み書きで待つあいだ、グリーンスレッドは順番をほかのスレッドに譲ります。つまり、待ち時間の多い、常駐するプログラムです。外からつないで中をのぞくには、ちょうどいい形をしています。

### Fluxpinelを組み込んだときのプロセスの中身

ここからは、あくまで現時点の想定です。Fluxpinelを組み込んだバイナリの中では、次のものが動く見込みです。

```
+-------------------------- build/blog/blog（1つのプロセス） -----------------------------+
|
|  グリーンスレッド（Spinelのスケジューラが回す）
|    [accept]   接続を待つ ---------> 接続ごとに [req] を立てる
|    [req]      リクエストを読む -> ルーティング -> コントローラ -> SQLite -> 応答を書く
|    [jobs]     ジョブのキューを待つ
|    [console]  127.0.0.1:4000 を待つ ---> 接続ごとに [sess] を立てる     <- 足すもの
|    [sess]     行を読む -> Fluxpinel.feed(session, line) -> 返事を書く   <- 足すもの
|
|  コンパイル済みのコード（Railsアプリとフレームワーク）  Fluxpinel（Rubyインタプリタ）
|  Spinelのランタイム: 1つのヒープ、1つのGC、例外、組み込みメソッド
+-----------------------------------------------------------------------------------------+
```

`[console]`と`[sess]`は、コンパイル済みのRubyとして書きます。ソケットを受けて、行を読み、Fluxpinelに渡し、返事を書くだけです。Fluxpinelが動くのは、`[sess]`が`Fluxpinel.feed`を呼んだときだけで、そのグリーンスレッドの上でコードを評価して戻ります。コンソールで`Console.count("Article")`を打つと、`[sess]`のスレッドがコンパイル済みの`Article.count`を呼びます。リクエストのスレッドが同じメソッドを呼ぶのと、やっていることは変わりません。

この形なら、ふだんのアプリの動きはほとんど邪魔しないはずです。

- **リクエストはFluxpinelを通らない**: リクエストのスレッドが実行するのは、コンパイル済みのコードだけ
- **待っているあいだは何もしない**: コンソールのスレッドは、ふだんはソケットを待っている。待っているグリーンスレッドはスケジューラから外れるから、CPUを使わない
- **評価のあいだも順番を独り占めしない**: 計算が長く続くスレッドには、ランタイムの監視スレッドが「順番を譲れ」と合図する。Fluxpinelも、ループの折り返しとブロックの呼び出しのたびに、この合図を確かめる。コンソールに重い処理を打っても、リクエストに順番が回る（ループやブロックを使わない深い再帰は除く）
- **値を写さない**: コンソールが持つオブジェクトはアプリと同じヒープにあって、同じGCが面倒を見る

難点はあります。Rubyのコードを動かすOSのスレッド（ワーカー）が1本になることです（後述）。コンソールで打った重い処理はそのぶんリクエストとCPUを分け合います。セッションは打ったコードを持ち続け、メモリ消費が少しずつ増えます。

## いまのFluxpinelができていること

| 項目 | 状態 |
|---|---|
| コンパイル済みのプログラムとFluxpinelをひとつのTUでビルドする | できている |
| スクリプトから、コンパイル済みのモジュールのメソッド（エントリ）を呼ぶ | できている |
| コンパイル済みのオブジェクトを値として持つ。`class`、`is_a?`、`inspect`、`==`を使う | できている |
| コンパイル済みのオブジェクトのインスタンス変数を読む（`instance_variable_get`） | できている |
| グリーンスレッドの上でスクリプトを動かす | できている |
| コンソールの評価（評価の単位、書きかけの行、行をまたぐローカル変数） | できている |
| 複数のOSスレッドで動くプログラムに組み込む | まだ |

コンソールの仕組みは、Fluxpinelの2つの関数です。コンパイル済みのコードが、ソケットから読んだ行をそのままFluxpinelに渡します。

```ruby
module Fluxpinel
  native_func :session, [], :any, "fx_api_session"
  native_func :feed, [:any, :string], :string, "fx_api_feed"
end

def serve_console(sock)
  session = Fluxpinel.session
  sock.write("fx> ")
  while (line = sock.gets)
    reply = Fluxpinel.feed(session, line)
    break unless reply   # exitでセッションが閉じた
    sock.write(reply)
  end
  sock.close
end
```

ソケットを扱うのは、コンパイル済みのコードの側です。Fluxpinelは、行を受け取って、返す文字列を作るだけ。

`Fluxpinel.feed`は、受け取った行をセッションのバッファにためて、毎回Prismがパースします。

セッションは、評価のたびにローカル変数を引き継ぎます。さきほどのコンソールが`a`を次の行で使えるのは、このためです。

コンソールで`exit`を打つと、閉じるのはセッションだけです。サーバはそのまま動き続けます。

### マルチスレッドはそのうち

表の最後の行「複数のOSスレッドで動くプログラムに組み込む」は、まだできません。Fluxpinelの内部の状態（メソッドの表やフレームのスタック）は、OSのスレッドをまたいで共有できるようにできていないからです。そこでFluxpinelは、組み込んだプログラムの、Rubyのコードを動かすOSのスレッド（ワーカー）の数を1に固定します（`SPINEL_WORKERS=1`）。ランタイムの監視スレッドは、これとは別のOSスレッドで動きます。

ブログのサーバも、1本のワーカーで動きます。グリーンスレッドは、1本のワーカーの上を順番に動きます。上の画面のとおり、ページもふつうに返ってきます（Roundhouseのサーバも、はじめは1本のOSスレッドで動いていました）。CPUのコアを1つしか使わないぶん、混んだときの速さは落ちます。

コンソールの評価にだけロックをかければ、リクエストの処理は複数のOSスレッドのまま並べて、コンソールだけを1本ずつ動かせるかもしれません。GCとの関係も含めて調べることが多いので、これは後回しにしています。

## Roundhouseへの提案

上の画面は、Roundhouseの出力に、3つの手作業を加えて作りました。この3つを、Roundhouseに提案したいと思っています。

### 1. サーバの起動をエントリに移す

Roundhouseが出力する`main.rb`は、ファイルのトップレベルでサーバを起動して、そのままリクエストを待ち続けます。

一方、Fluxpinelを組み込んだバイナリでは、Fluxpinelが動き出せるのは、コンパイル済みのプログラムのトップレベルが終わったあとです。トップレベルでサーバのループに入られると、Fluxpinelの出番が来ません。

そこで、サーバを起動する部分をメソッド（たとえば`Main.start`）に移してもらい、バイナリはそのメソッドから始まるようにしたい。コンソールのスレッドもそこに立てます。こんな感じ:

```ruby
module Main
  def self.start(argv)
    # ...（もとはトップレベルにあったコード）
    console_port = ENV["FLUXPINEL_CONSOLE"].to_s.to_i
    Thread.new { Console.listen(console_port) } if console_port > 0
    Tep::Server::Threaded.new(MainApp.new).run(port, workers, false, unix_listener)
  end
end
```

### 2. コンソール用のエントリを生成する

`Console.count("Article")`のような入口は、モデルごとに分岐するメソッドです。

```ruby
module Console
  def self.count(model)
    case model
    when "Article" then Article.count
    when "Comment" then Comment.count
    else raise ArgumentError, "unknown model: #{model}"
    end
  end
end
```

Spinelは、文字列から実行時にクラスを探して呼ぶコードをコンパイルできないから、こういう`case`で書く必要があります。Roundhouseはもともと、ルーティングの表からコントローラーを選ぶところを、同じ形の`case`で出力しています。Roundhouseはモデルの一覧も知っているから、`count`、`find`、`where`、`create`、`update`のような入口を生成するのは、Roundhouseの得意な仕事のはずです。

### 3. Fluxpinelを組み込むルート

Fluxpinelを組み込むビルドは、ふつうの`spin build`とは手順が違います。Spinelにコンパイル済みのプログラムをライブラリとしてCに出力させて、FluxpinelのCのコードと合わせて、ひとつの翻訳単位としてコンパイルします。今回は、Fluxpinelの`make host`に、`spin`がSpinelに渡すフラグ（RBSの場所など）とリンクするライブラリ（SQLiteなど）を手で渡しました。Roundhouseの出力に、このビルドを選ぶオプション（たとえば`--console`）があれば、使う人はビルドの細かい手順を知らずに済みます。

## Spinelへの提案

ここまでの形で、上の画面は作れました。ただ、`Console.count("Article")`というのがぜんぜんRubyらしくありません。ここから先はSpinelの変更が要ります。

### コンパイル済みのオブジェクトのメソッドを呼ぶ

いまSpinelがエクスポートできるのは、モジュールのメソッドだけです。だから、スクリプトから`a.title`とは書けず、インスタンス変数を直接読むか、エントリを経由するしかありません。

Spinelが、コンパイル済みのオブジェクトのメソッドを名前で呼ぶ口を出せるようになれば、コンソールで`a.title`や`Article.where(...).count`とそのまま書けます。Roundhouseがコンソール用のエントリを生成する必要もなくなります。[(1)eval編](/2026/10/24/fluxpinel-1.html)で「動的ディスパッチ」として書いた変更と同じ理屈です。

### spinがFluxpinelを組み込む

Roundhouseの出力は`spin`のプロジェクトです。ところが`spin`がライブラリとしての出力を使うのは、CRubyの拡張ライブラリを作るときだけです。アプリのビルドで、Fluxpinelのようなホストと一緒にコンパイルする道を`spin`に用意してもらえれば、Roundhouseのオプションはその上に作れます。

複数のOSスレッドとの共存は、先に書いたとおり、とりあえずFluxpinelの側の課題です。Spinelのランタイムにパッチが必要かどうかは、まだわかりません。

## 任意のRailsアプリではどう使えるか

Roundhouseが任意のRailsアプリを変換できるなら、変換したバイナリにFluxpinelを組み込んで、次のように使えます。

- **本番のバイナリでの`rails console`**: レコードを数える、探す、壊れたレコードを直す、といった作業を、動いているバイナリに対して行う
- **動いているプロセスの中を見る**: ジョブのキューの長さ、キャッシュの中身、Action Cableの購読の数など、プロセスの中にしかない状態を、エントリを通して読む
- **再起動しない設定の切り替え**: ログの細かさや機能フラグを、コンパイル済みのコードがFluxpinelに問い合わせる形にしておけば、コンソールから切り替えられる
- **`rails runner`の代わり**: 一回きりのデータの修正スクリプトを、コンソールから`load`で動いているプロセスに流し込む。再コンパイルもデプロイも要らない

できないこともはっきりしています。コンパイル済みのメソッドは差し替えられません。コンソールで`Article#title`を再定義しても、コンパイル済みのコードは古い`title`を呼びます。

コンソールは、同じプロセスの中のことならなんでもできてしまい危険なので、ソケットはUNIXドメインソケットにだけ開くべきでしょう。`127.0.0.1`には、同じマシンのほかのユーザもつなげます。認証もありません。パーミッションで守れるUNIXドメインソケットのほうがいくらか安全です。

## まとめ

Roundhouseは、Railsアプリを静的な形に書き下して、Spinelで速いバイナリにします。Fluxpinelは、その静的なバイナリに、もう一度Rubyの動的なところを差し込みます。逆向きの道具のようですが、組み合わせると、速さを保ったまま`rails console`の便利さを取り戻せます。

Roundhouseの出力を手で直すなら、すでに動いています。この手作業をなくせるよう、動いた差分を持ってRoundhouseとSpinelに提案できたらいいなと思っています。
